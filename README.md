# Research State Engine (연구 상태 엔진)

2026 NAIS AI 해커톤 본선 · 더블에이파트너스

연구자가 따로 기록하지 않아도 대화로 말한 **실제 시도·실패가 연구 상태로 쌓이고**, 그것이 **다음 판단에 다시 쓰이며**,
근거 논문이 나중에 **철회되면 그 근거를 썼던 과거 판단까지 재검토 대상으로 표시**하는 단일 애플리케이션입니다.
되돌릴 수 없는 작업(원본 덮어쓰기 등)만 사람 승인을 기다리고, 그동안 다른 가역 작업은 계속됩니다.

> **기관 시도 이력과 과거 판단은 시연용 합성 데이터 · 문헌 근거와 철회 정보는 공개 실제 데이터**

## 증명하는 네 가지

| | 무엇이 실제로 작동하는가 |
|---|---|
| A. 자동 축적 | "오늘 ~를 측정했고 ~단계에서 중단했습니다" → 저장 폼·확인 버튼 없이 시도가 구조화되어 SQLite 에 저장. 계획·질문은 저장하지 않음 |
| B. 재사용 | 다음 질문에서 같은 접근(대상+방법+환경)의 과거 시도 수와 중단 단계를 DB 실제값으로 계산해 답함 |
| C. 근거 검증·소급 | Crossref 로 DOI 를 확인(확인 / 서지 불일치 / 확인 불가 / 철회됨). [지금 재검사] 로 철회가 확인되면 그 근거를 쓴 과거 판단에 "재검토 필요" 표시 |
| D. 비가역만 승인 | 원본 덮어쓰기는 승인 대기열로. 승인 전·후 SHA-256 을 나란히 표시. 대기 중에도 분석 작업은 완료 |

## 문제

연구실의 실패·중단 흔적은 연구노트나 실험 보고서 속에 남아 있더라도 구조화된 조직의 연구 상태로 연결되어 있지 않아, 다음 연구자가 검색·재사용하기 어렵습니다.
새로 생기는 실패는 별도 기록 부담 때문에 아예 남지 않기도 합니다. 그래서 같은 접근이 반복됩니다.
판단의 근거였던 논문이 나중에 철회되어도, 그 논문을 근거로 내린 과거 판단은 아무도 다시 보지 않습니다.

## 화면

| 화면 | 역할 |
|---|---|
| A 연구 대화 | 자연어로 결과를 말하거나 질문. 답은 세 덩어리: 이미 해본 것(같은 접근 N건·중단 단계) · 근거 상태 · 다음 후보 |
| B 승인 대기열 | 비가역 작업 카드(작업·승인 이유·영향 대상·hash 앞 8자리), 승인/거절, 승인 전·후 hash 나란히 |
| C 연구 상태 | 자동 축적된 시도(원문 + 구조화 값), 근거 상태, 판단의 재검토 표시, 상단 [지금 재검사] |

## 시연 흐름 (G1~G6)

실제 구현·검증 상태는 [docs/STATUS.md](docs/STATUS.md) 가 기준입니다 (2026-09-30 main 실측: `npm test` 74/74 · API/DB 검증 74/74 · 실제 브라우저 화면 검증 29/29, G1~G6 PASS).

1. **G1 자동 축적** — baseline 같은 접근 2건 → "오늘 후보 단백질 RSE-01을 세포 모델에서 Western blot으로 측정했고, 재현성 검증 단계에서 중단했습니다." → 저장 확인 없이 3건, 화면 C 새 행. 계획·질문은 0건 증가
2. **G2 재사용** — 다시 질문 → "이 접근은 3번 시도됐고 모두 재현성 검증 단계에서 멈췄습니다" (DB 실제값 계산)
3. **G3 근거 검증** — 정상 DOI → 확인 · 시연용 손상 표본 → 서지 불일치 · Crossref 미확인 DOI → 확인 불가 · 조회 실패는 기존 확인을 덮어쓰지 않음
4. **G4 철회와 소급** — 2022-03-15 합성 과거 판단(근거: Aβ*56 논문, 당시 확인) → [지금 재검사] → 현재 Crossref 에서 철회 확인 → 철회됨 + 연결된 판단에 "재검토 필요" (판단이 틀렸다는 뜻이 아님)
5. **G5 승인 게이트** — 원본 덮어쓰기 요청 → 대기, 승인 전 hash 불변 · 대기 중 분석 1건 완료 · 승인 후 hash 변경
6. **G6 영속성** — 서버 재시작 후 시도·근거·연결·철회 상태·재검토 표시 유지

## 확장성 — 도입 첫날의 과거 데이터 (콜드스타트)

> 질문: "처음 도입하면 과거 실패 데이터는 어디서 가져오는가?"

실제 연구기관에는 연구노트·ELN·실험 보고서·프로젝트 폴더·분석 기록에 과거 시도 흔적이 이미 있을 수 있습니다.
문제는 기록이 없다는 것이 아니라, 그 기록이 **구조화된 조직의 연구 상태로 연결되어 있지 않다**는 것입니다.
이 프로젝트는 이를 세 단계로 봅니다. **이번 본선 프로토타입이 실제로 구현·검증한 것은 ② 단계뿐**입니다.

| 단계 | 내용 | 상태 |
|---|---|---|
| ① 도입 초기 — Research Memory Bootstrap | 기존 기록에서 과거 **시도 후보**를 읽어 Research State 후보로 구조화 | **향후 확장** (미구현) |
| ② 도입 이후 — 자동 축적과 재사용 | 연구자가 별도 실패 보고서를 쓰지 않아도, 평소 연구 대화에서 말한 실제 실행·중단 흔적이 자동 축적되고 다음 판단에 재사용 | **현재 구현** (G1~G6, [docs/STATUS.md](docs/STATUS.md)) |
| ③ 조직의 지속되는 연구 기억 | 시도·근거·내부 판단·근거 상태 변화가 연결되어, 연구자가 바뀌어도 이어서 확인 가능 | **확장 방향** |

```
기존 연구노트·ELN·실험기록              ┐
        ↓ (향후 확장)                    │ ① 도입 초기
과거 시도 후보 추출                      │   Research Memory Bootstrap
        ↓                                │
출처·원문과 함께 Research State 후보로 구조화 ┘
        ↓
도입 이후 신규 시도 자동 축적 · 재사용   ── ② 현재 프로토타입이 구현
        ↓
조직의 지속되는 연구 기억               ── ③ 확장 방향
```

**① 도입 초기 — Research Memory Bootstrap (향후 확장)**
기존 자료를 모두 자동으로 사실화하는 것이 아닙니다. 과거 시도 **후보**를 회수하되 다음 원칙을 지키는 방향입니다.
- 자동으로 사실을 확정하지 않는다 — 과거 자료에서 추출한 **후보**라는 출처 표시를 달고, 검증 전에는 확정된 조직 사실로 쓰지 않는다
- 출처 파일과 원문을 보존하고, 가능한 경우 원 기록의 날짜도 함께 보존한다
- 대상·방법·환경이 불명확하면 미확정으로 둔다 (같은 접근 판정에 쓰지 않음)

이 원칙은 현재 구현의 규칙을 그대로 잇는 것입니다. 현재도 원문과 구조화 값을 함께 저장하고(`*_raw` / `*_norm`), 미상 값은 NULL 로 두어 같은 접근을 확정하지 않으며, 계획·질문·가설은 시도로 저장하지 않습니다.

**② 도입 이후 — 현재 구현**
- 자연어로 말한 실제 실행 결과의 자동 축적 (저장 폼·확인 버튼 없음)
- 저장된 연구 상태의 재사용 (같은 접근 N건·중단 단계를 DB 실제값으로 계산)
- Crossref 근거 상태 검증과, 근거 상태 변화의 과거 판단 소급 표시
- 비가역 작업만 승인 대기

**③ 조직의 지속되는 연구 기억 (확장 방향)**
시도·근거·판단·근거 상태 변화가 계속 연결되면, 다음 연구자는 "이 접근을 이미 시도했는가 · 몇 번 · 어디서 멈췄는가 · 어떤 근거를 썼는가 · 그 근거 상태가 이후 바뀌었는가"를 이어서 확인할 수 있습니다.
기존 기록 import, ELN·LIMS 연동, 프로젝트 파일에서의 후보 추출, 조직 단위 Bootstrap 은 모두 **향후 연동 가능한 확장 단계**이며 이번 프로토타입에는 없습니다.

확장성의 두 축:
- **도입 가능성** — 기존 기록이 있는 기관도 처음부터 모든 데이터를 새로 만들 필요 없이, 과거 기록을 한 번 후보로 회수해 시작할 수 있는 확장 방향
- **지속성** — 그 이후에는 신규 시도가 자동 축적되어 조직의 연구 기억이 계속 커지는 구조 (현재 구현된 부분)

> 한 줄 요약: **과거 기록은 한 번 구조화하고, 그다음부터는 실패가 다시 문서 속에 묻히지 않게 합니다.**

**예상 질문** — "연구원들이 실패 사례를 잘 공유하지 않는데, 처음 데이터는 어떻게 만듭니까?"
두 단계로 봅니다. 도입 초기에는 기존 연구노트나 실험 보고서에서 과거 시도 후보를 회수하되, 원문과 출처를 함께 보존하고 불명확한 내용은 확정하지 않습니다. 그 이후부터는 현재 프로토타입처럼 연구자가 별도 실패 보고서를 작성하지 않아도 실제 연구 대화와 실행 과정에서 새로운 시도가 자동으로 축적됩니다. 이번 본선에서는 두 번째 단계인 자동 축적과 재사용을 실제 구현했고, 기존 기록을 가져오는 부트스트랩은 확장 단계입니다.

## 실행

```bash
npm run db:init          # SQLite schema 생성 (DB_PATH, 기본 var/rse.db)
npm run seed             # 빈 DB 에 시연 seed 적재
npm start                # http://127.0.0.1:4100
npm test                 # 단위·통합 테스트 (네트워크 불필요)
node scripts/verify-gates.js   # G1~G6 실서버·실DB·실Crossref 통합 검증 (var/verify 사용)
```

화면 흐름 검증 (Windows 에서, Chrome 필요): `node \\wsl.localhost\Ubuntu\home\user\projects\Research_State_Engine\scripts\verify-ui.js`

시연 전 baseline 복원 (제품 기능이 아닌 운영 절차):

```bash
npm run baseline:create  # 기능 동결 후 1회: var/baseline/rse.baseline.db 생성
npm run baseline:restore # 서버 정지 상태에서 복원 → 4값 검사 (4/4 아니면 시연 시작 금지)
```

## 기술 구성

| 구분 | 사용 |
|---|---|
| 런타임 | Node.js ≥ 22.13 (외부 npm 의존성 없음) |
| 서버 | `node:http` 단일 애플리케이션 |
| 저장소 | **SQLite** 단일 파일 (`node:sqlite`) — 연구 시도·근거·판단·연결·승인·Crossref 조회 cache |
| 테스트 | `node:test` |
| 외부 연구 데이터 | **Crossref REST API** (`api.crossref.org/works/{doi}`) 하나뿐 |
| 무결성 | SHA-256 (`node:crypto`) |
| AI 모델 | 자연어 → 구조화 후보 추출: 로컬 Claude Code CLI (`claude -p`, 계정 기본 모델 — 2026-09-30 실측 `modelUsage`: `claude-sonnet-5`, 보조 `claude-haiku-4-5-20251001`). CLI 실패 시 규칙 기반 추출로 전환하고 응답에 `extractor_fallback` 표기 · 개발 도구: Claude Code (Claude Opus 5.5) |

LLM 은 값 추출·설명에만 쓰이며, 다음은 결정적 규칙(코드)이 판정합니다:
실행 흔적 여부 · 같은 접근 여부 · 서지 비교 · 철회 판정 · 조회 실패 시 기존 상태 유지 · 승인 필요 여부.
