# Research State Engine (연구 상태 엔진)

2026 NAIS AI 해커톤 본선 · 더블에이파트너스

Research State Engine 은 논문 자체가 아니라 **연구 시도의 상태를 축적·재사용하는 엔진**입니다.
연구자가 에이전트와의 대화에서 말한 **실제 실행·중단이 별도 저장 폼이나 확인 단계 없이 연구 상태로 쌓이고**, 그것이 **다음 판단에 다시 쓰이며**,
근거 논문이 나중에 **철회되면 그 근거를 썼던 과거 판단까지 재검토 대상으로 표시**하는 단일 애플리케이션입니다.
되돌릴 수 없는 작업(원본 덮어쓰기 등)만 사람 승인을 기다리고, 그동안 다른 가역 작업은 계속됩니다.

기본 단위는 논문이 아니라 **연구 시도**입니다. 논문·DOI 는 그 시도와 판단에 연결된 **근거**입니다.

```
연구 시도 → 그 시도·판단에 사용된 근거 → 연구 판단 → 근거 상태가 바뀌면 연결된 판단을 재검토
```

중단·실패는 특별히 중요한 상태이지만, 제품은 실패 수집기가 아니라 시도·근거·판단의 상태를 잇는 것을 목표로 합니다.
"자동"은 **대화 입력 뒤의 별도 저장 단계가 없다**는 뜻입니다. 현재 입력은 연구자가 에이전트 대화에 말한 내용이며, 시스템이 실제 장비·실험 행동을 감지하는 것이 아닙니다.
계획·질문·가설은 연구 시도로 저장하지 않고, 실제 실행·결과 흔적이 있는 발화만 시도로 취급합니다.

> **기관 시도 이력과 과거 판단은 시연용 합성 데이터 · 문헌 근거와 철회 정보는 공개 실제 데이터**

## 증명하는 네 가지

| | 무엇이 실제로 작동하는가 |
|---|---|
| A. 대화 기반 축적 | 연구자가 "오늘 ~를 측정했고 ~단계에서 중단했습니다" 라고 말하면 → 저장 폼·확인 버튼 없이 시도가 구조화되어 SQLite 에 저장. 계획·질문·가설은 저장하지 않음 (장비 행동을 자동 감지하지 않음) |
| B. 재사용 | 다음 질문에서 같은 접근(대상+방법+환경)의 과거 시도 수와 중단 단계를 DB 실제값으로 계산해 답함 |
| C. 근거 검증·소급 | Crossref 로 DOI 를 확인(확인 / 서지 불일치 / 확인 불가 / 철회됨). [지금 재검사] 로 철회가 확인되면 그 근거를 쓴 과거 판단에 "재검토 필요" 표시 |
| D. 비가역만 승인 | 원본 덮어쓰기는 승인 대기열로. 승인 전·후 SHA-256 을 나란히 표시. 대기 중에도 분석 작업은 완료 |

## 문제

연구실의 실패·중단 흔적은 연구노트나 실험 보고서 속에 남아 있더라도 구조화된 조직의 연구 상태로 연결되어 있지 않아, 다음 연구자가 검색·재사용하기 어렵습니다.
새로 생기는 실패·중단은 별도 기록 부담 때문에 남지 않는 경우도 있습니다. 그러면 같은 접근이 반복될 수 있습니다.
판단의 근거였던 논문이 나중에 철회되어도, 그 논문을 근거로 내린 과거 판단을 다시 살펴보게 하는 연결이 없으면 놓치기 쉽습니다.

## 화면

| 화면 | 역할 |
|---|---|
| A 연구 대화 | 자연어로 결과를 말하거나 질문. 답은 세 덩어리: 이미 해본 것(같은 접근 N건·중단 단계) · 근거 상태 · 다음 후보 |
| B 승인 대기열 | 비가역 작업 카드(작업·승인 이유·영향 대상·hash 앞 8자리), 승인/거절, 승인 전·후 hash 나란히 |
| C 연구 상태 | 대화에서 축적된 시도(원문 + 구조화 값), 근거 상태, 판단의 재검토 표시, 상단 [지금 재검사] |

## 시연 흐름 (G1~G6)

실제 구현·검증 상태는 [docs/STATUS.md](docs/STATUS.md) 가 기준입니다 (2026-09-30 실측: `npm test` 78/78 · `verify-gates` API/DB 검증 74/74 · `verify-ui` 실제 브라우저 화면 검증 29/29 · LLM 경로 리허설 3/3, G1~G6 PASS).

1. **G1 대화 기반 축적** — baseline 같은 접근 2건 → "오늘 후보 단백질 RSE-01을 세포 모델에서 Western blot으로 측정했고, 재현성 검증 단계에서 중단했습니다." → 저장 확인 없이 3건, 화면 C 새 행. 계획·질문은 0건 증가
2. **G2 재사용** — 다시 질문 → "이 접근은 3번 시도됐고 모두 재현성 검증 단계에서 멈췄습니다" (DB 실제값 계산)
3. **G3 근거 검증** — 정상 DOI → 확인 · 시연용 손상 표본 → 서지 불일치 · Crossref 미확인 DOI → 확인 불가 · 조회 실패는 기존 확인을 덮어쓰지 않음
4. **G4 철회와 소급** — 2022-03-15 합성 과거 판단(근거: Aβ*56 논문, 당시 확인) → [지금 재검사] → 현재 Crossref 에서 철회 확인 → 철회됨 + 연결된 판단에 "재검토 필요" (판단이 틀렸다는 뜻이 아님)
5. **G5 승인 게이트** — 원본 덮어쓰기 요청 → 대기, 승인 전 hash 불변 · 대기 중 분석 1건 완료 · 승인 후 hash 변경
6. **G6 영속성** — 서버 재시작 후 시도·근거·연결·철회 상태·재검토 표시 유지

## 확장성 — 도입 첫날의 과거 데이터 (콜드스타트)

> 질문: "처음에는 내부 데이터가 없는데 왜 쓰는가?" · "문서에 남기지 않은 실패 경험은 어떻게 가져오는가?"

실제 연구기관에는 연구노트·ELN·실험 보고서·분석 파일·프로젝트 기록에 과거 시도 흔적이 이미 있을 수 있습니다.
문제는 기록이 전혀 없다는 것이 아니라, 그 기록이 **구조화된 조직의 연구 상태로 연결되어 있지 않다**는 것입니다.
그리고 일부 경험은 문서에 남지 않고 연구자의 기억에만 있습니다.
내부 시도 이력이 0인 첫날부터 과거 실패를 알고 있다고 주장하지 않습니다.
아래 다섯 덩어리 중 **이번 본선 프로토타입이 실제로 구현·검증한 것은 C(도입 이후 대화 기반 축적)와 D(첫날 근거 검증)뿐**이고, A·B·E 는 향후 확장입니다.

| | 대상 | 방식 | 상태 |
|---|---|---|---|
| A | 문서에 남아 있는 과거 경험 | 기존 기록에서 과거 **시도 후보** 회수 (Research Memory Bootstrap) | **향후 확장** — 이번 프로토타입에 없음 |
| B | 문서에 남지 않은 경험 | 인수인계 시점의 짧은 AI 인터뷰로 **시도 후보** 회수 | **향후 확장** — 이번 프로토타입에 없음 |
| C | 도입 이후의 새 시도 | 연구자가 에이전트와의 대화에서 말한 실제 실행·중단을 별도 저장 단계 없이 구조화·축적, 다음 판단에 재사용 | **현재 구현** (G1~G6, [docs/STATUS.md](docs/STATUS.md)) |
| D | 첫날 (내부 시도 이력이 비어 있을 때) | 사용자가 제공한 DOI·서지의 현재 서지·철회 상태 검증 | **현재 구현** (보조 효용) |
| E | 장기 | 과거 후보 회수 + 이후 대화 기반 축적 → 사람이 바뀌어도 이어지는 조직의 연구 기억 | **확장 방향** |

```
[A 문서에 남은 경험]  기존 연구노트·보고서·분석 기록 ─┐
                                                        ├→ 시도 후보 (출처·원문·시점 보존, 불명확하면 미확정)   ← 향후 확장
[B 문서에 없는 경험]  인수인계 시점 짧은 AI 인터뷰 ────┘
        ↓ (검토 후 활용)
[C 도입 이후]  에이전트 대화에서 말한 실제 실행·중단 → 구조화(저장 단계 없음) → Research State 축적 → 재사용   ← 현재 구현
        ↓
[E 장기]  사람이 바뀌어도 이어지는 조직의 연구 기억   ← 확장 방향
```

**A. 문서에 남아 있는 과거 경험 — Research Memory Bootstrap (향후 확장, 미구현)**
향후 도입 단계에서는 기존 연구노트·실험 보고서·분석 파일·프로젝트 기록·ELN 에서 과거 **연구 시도 후보**를 추출하는 방향을 생각합니다.
기존 자료를 모두 자동으로 사실화하는 것이 아닙니다.
- 추출한 내용은 곧바로 사실로 확정하지 않고, "과거 기록에서 추출된 후보"임을 구분해 표시한다
- 출처와 원문을 보존하고, 가능한 경우 원 기록의 날짜도 함께 보존한다
- 대상·방법·환경 등이 불명확하면 미확정으로 둔다 (같은 접근 판정에 쓰지 않음)
- 검증되지 않은 후보는 확정된 조직 연구 상태처럼 쓰지 않는다

**B. 문서에 남지 않은 경험 — 인수인계 AI 인터뷰 (향후 확장, 미구현)**
퇴사·이동·과제 종료·인수인계 시점에, AI 가 "어떤 방법을 시도했는가 · 어디까지 진행했는가 · 어디에서 멈췄는가" 같은 짧고 구조화된 질문으로 연구자의 경험을 회수하는 방식을 향후 기관 도입 방향으로 생각합니다.
답변도 곧바로 사실로 확정하지 않습니다: 연구자 답변 → Research State **후보**로 구조화 → 원 발화·출처·시점 보존 → 불명확한 값은 미확정 → 필요한 검토 후 조직 연구 상태로 활용.
이 인터뷰는 이번 프로토타입에 구현되어 있지 않습니다.

**C. 도입 이후 — 현재 구현**
- 연구자가 에이전트와의 대화에서 말한 실제 실행·중단이 저장 폼·확인 버튼 없이 구조화·축적된다 (계획·질문·가설은 시도로 저장하지 않음, 실제 실행·결과 흔적이 있는 발화만 시도)
- 저장된 연구 상태를 다음 질문에서 재사용한다 (같은 접근 N건·중단 단계를 DB 실제값으로 계산). 질문은 판단(judgment)으로 저장되고 사용한 시도가 연결된다. 사용할 수 있는 검증된 근거가 있으면 판단과 근거도 연결된다
- 연결된 근거의 상태를 Crossref 로 다시 검사하고, 철회 관계가 확인되면 그 근거에 연결된 과거 판단에 재검토(`needs_review`) 표시를 붙인다
- 비가역 작업만 승인 대기한다

현재 구현이 받아들이는 입력은 **연구자가 대화에서 말한 내용**입니다. 실험 장비·ELN·메신저·파일 활동을 시스템이 스스로 감지하지 않습니다.
A·B 의 원칙은 현재 구현의 규칙을 그대로 잇습니다. 현재도 원문과 구조화 값을 함께 저장하고(`*_raw` / `*_norm`), 미상 값은 NULL 로 두어 같은 접근을 확정하지 않습니다.

**D. 첫날의 보조 효용 — 현재 구현**
내부 시도 이력이 아직 비어 있어도, 사용자가 제공한 DOI·서지에 대해서는 현재 서지·철회 상태 검증을 바로 쓸 수 있습니다. Crossref 가 하는 일은 서지·철회 관계 상태 확인이며, 실패 원인을 알려주거나 판정하지 않습니다.
이것은 보조 효용이며, 제품의 중심은 논문 검색이 아니라 연구 시도의 축적·재사용입니다.

**E. 조직의 지속되는 연구 기억 — 확장 방향**
시도·근거·내부 판단·근거 상태 변화가 계속 연결되면, 특히 담당자 변경·인수인계·장기간 뒤 프로젝트 재개 같은 상황에서 다음 사람은 "이 접근을 이미 시도했는가 · 몇 번 · 어디서 멈췄는가 · 어떤 근거를 썼는가 · 그 근거 상태가 이후 바뀌었는가"를 이어서 확인할 수 있습니다.
기존 기록 import, ELN·LIMS 연동, 연구 플랫폼 통합, 대화를 연구노트 초안으로 연결하는 기능, 프로젝트 파일에서의 후보 추출, 조직 단위 Bootstrap, 인수인계 AI 인터뷰는 모두 **향후 확장 단계**이며 이번 프로토타입에는 없습니다. 흔적이 전혀 없는 과거 실패를 복원할 수 있다고 주장하지 않습니다.

**기관 적용 시 고려사항 (향후 운영·거버넌스 과제)**
실제 기관 적용에는 실패 이력의 접근권한·공유범위·평가 활용 정책 설계가 별도로 필요합니다. 이번 프로토타입에는 권한·공유범위 기능이 없습니다.

확장성의 두 축:
- **도입 가능성** — 기존 기록이 있는 기관도 처음부터 모든 데이터를 새로 만들 필요 없이, 문서에 남은 경험과 문서에 없는 경험을 후보로 회수해 시작할 수 있는 확장 방향 (A·B)
- **지속성** — 그 이후에는 대화에서 말한 새 시도가 별도 저장 단계 없이 축적되는 구조 (C, 현재 구현은 이 메커니즘까지이며, 지속 사용 여부는 아래 제품 가설)

> 한 줄 요약: **연구자가 말한 시도와 중단이 별도 기록 단계 없이 연구 상태로 남고, 이후 판단과 근거 상태 재검토에 다시 쓰입니다.**

**예상 질문** — "연구원들이 실패 사례를 잘 남기지 않는데, 처음 데이터는 어떻게 만듭니까?"
내부 이력이 없는 첫날부터 과거 실패를 안다고 주장하지 않습니다. 첫날에는 사용자가 연결한 DOI·서지의 현재 근거 상태 검증이라는 보조 효용이 있고, 도입 이후에는 에이전트 대화에서 말한 실제 실행·중단이 별도 기록 단계 없이 누적됩니다. 가치는 담당자 변경·인수인계·프로젝트 재개 시점에 특히 커질 것으로 봅니다. 과거 기록 회수는 두 종류로 나눠 봅니다. 기록에 남아 있는 것은 향후 도입 단계에서 출처와 원문을 보존한 과거 시도 후보로 구조화할 수 있고, 문서에 남지 않은 경험은 퇴사나 과제 종료 같은 인수인계 시점에 짧은 AI 인터뷰로 회수하는 방향을 생각하고 있습니다. 이 두 방식은 향후 확장입니다. 이번 프로토타입에서는 연구자가 에이전트와의 대화에서 말한 실제 실행과 중단을 별도 저장 단계 없이 구조화하고 다음 판단에서 재사용하는 부분을 구현했습니다.

**예상 질문** — "연구자가 처음부터 왜 이 시스템을 씁니까?"
기록을 별도 업무로 만들지 않는 것이 설계 가설이며, 연구자가 계속 쓰는 동기는 아직 사용자 파일럿에서 검증해야 할 제품 가설입니다. 이번 프로토타입이 검증한 것은 사용 동기가 아니라 기술 메커니즘 — 대화 → 시도 상태 축적 → 재사용 → 근거 상태 변화 → 연결된 과거 판단 재검토 — 입니다. 초기에도 사용자가 연결한 근거 논문의 현재 상태를 확인하는 효용은 있지만, 지속 사용의 진입점은 연구 계획·문헌 확인·연구 정리처럼 원래 하던 업무를 이 환경에서 처리하게 하는 방향으로 후속 파일럿에서 검증하려고 합니다 (대화를 연구노트 초안으로 연결하는 사용 경험 포함 — 현재 미구현).

**예상 질문** — "Weights & Biases 같은 MLOps 도구와 무엇이 다릅니까?"
MLOps 가 주로 코드로 실행되는 머신러닝 실험의 파라미터와 결과를 추적한다면, Research State Engine 은 일반 R&D 에서 시도·근거·판단의 상태와 근거 상태 변화를 연결하는 방향을 목표로 합니다. MLOps 도구의 대체재나 완성된 범용 연구 플랫폼을 주장하지 않으며, 현재는 그 방향의 프로토타입입니다.

## 실행

```bash
npm run db:init          # SQLite schema 생성 (DB_PATH, 기본 var/rse.db)
npm run seed             # 빈 DB 에 시연 seed 적재
npm start                # http://127.0.0.1:4100
npm test                 # 단위·통합 테스트 (네트워크 불필요)
node scripts/verify-gates.js   # G1~G6 실서버·실DB·실Crossref 통합 검증 (var/verify 사용)
```

화면 흐름 검증 (Windows 에서, Chrome 필요): `node \\wsl.localhost\Ubuntu\home\user\projects\Research_State_Engine\scripts\verify-ui.js`

시연 전 baseline 복원 (제품 기능이 아닌 운영 절차):

```bash
npm run baseline:create  # 기능 동결 후 1회: var/baseline/rse.baseline.db 생성
npm run baseline:restore # 서버 정지 상태에서 복원 → 4값 검사 (4/4 아니면 시연 시작 금지)
```

## 기술 구성

| 구분 | 사용 |
|---|---|
| 런타임 | Node.js ≥ 22.13 (외부 npm 의존성 없음) |
| 서버 | `node:http` 단일 애플리케이션 |
| 저장소 | **SQLite** 단일 파일 (`node:sqlite`) — 연구 시도·근거·판단·연결·승인·Crossref 조회 cache |
| 테스트 | `node:test` |
| 외부 연구 데이터 | **Crossref REST API** (`api.crossref.org/works/{doi}`) 하나뿐 |
| 무결성 | SHA-256 (`node:crypto`) |
| AI 모델 | 자연어 → 구조화 후보 추출: 로컬 Claude Code CLI (`claude -p`, 계정 기본 모델). CLI 실패 시 규칙 기반(rules) 추출로 전환하고 응답에 `extractor_fallback` 을 표기해 숨기지 않음. 2026-09-30 API Key 인증 복구 후 제품 추출 함수 실측 `modelUsage` = `claude-sonnet-5-5` (관측값이며 코드에 고정하지 않음). 그 환경에서 제품 실제 extractor = `llm:claude-cli`, 정상 경로 unexpected fallback 0, LLM 경로 리허설 3/3. LLM 이 넘긴 값은 원문에 글자 그대로 있는 것만 쓰고, 대상에 붙은 환경 표현·누락된 환경은 원문 규칙으로 보정 · 개발 도구: Claude Code (Claude Opus 5.5) |

LLM 은 값 추출·설명에만 쓰이며, 다음은 결정적 규칙(코드)이 판정합니다:
실행 흔적 여부 · 같은 접근 여부 · 서지 비교 · 철회 판정 · 조회 실패 시 기존 상태 유지 · 승인 필요 여부.

**합성 seed · 공개 실제 데이터 · 현재 작동 · 향후 확장의 구분**
- **본선 시연용 합성 seed**: 본선 시작 전에 기관에 존재했다고 가정한 과거 연구 시도 이력, Aβ*56 근거와 연결된 2022-03-15 과거 내부 판단 (실제 기관 기록이 아님)
- **공개 실제 데이터**: Aβ*56 논문, DOI, 현재 Crossref 에서 조회하는 서지·철회 관계 정보
- **현재 실제 작동 (runtime)**: 새 대화 입력의 시도 저장, DB 재사용(같은 접근 재계산·질문 판단 저장), Crossref 재검사, 근거 상태 변화에 따른 연결 판단 재검토 표시, 비가역 작업 승인 게이트
- **향후 확장 (미구현)**: 위 "확장성" 절의 Bootstrap·인수인계 AI 인터뷰·연구노트 초안 연결·ELN/LIMS 연동·플랫폼 통합

seed 는 시연 시작 상태를 미리 준비한 것이고, 그 위에서 일어나는 저장·계산·조회·재검사는 실제 runtime 이 수행합니다.

데모1(RSE-01 합성 이력)과 데모2(Aβ*56 철회 논문) 사이에는 어떤 인과관계도 없습니다.
"확인 불가"는 Crossref 에서 확인하지 못했다는 뜻이며 논문이 없다는 뜻이 아닙니다. DOI 확인은 논문 주장의 과학적 참을 뜻하지 않습니다.
